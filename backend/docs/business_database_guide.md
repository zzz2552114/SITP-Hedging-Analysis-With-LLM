# 主营业务分析数据库说明文档

此文档主要针对 `company_yearly_main_business` 表（公司年度主营业务表）的设计思路及使用说明进行阐述。

## 1. 设计初衷与在架构中的位置

大模型解析后的输出主要落地在 `hedging_business_detail`（套期保值明细表）。
但是，为了实现**“对比同一主营业务下哪些公司开展套保哪些不开展，并提供汇总套保额度与商品列表（渗透率统计）”** （需求4），我们需要一个前置或者并行的表来记录：**在某个自然年，市面上有哪些上市公司，且它们各自的主营业务是什么**。

只有拥有了完整的“某行业/核心业务下的全部公司基数”，我们才能用“有套保明细的公司数量”除以“这个基数”，从而计算出套保的**渗透率**。这就是建立 `company_yearly_main_business`（及 `listed_company_base` 根表）的核心目的。

## 2. 表结构详解

### 2.1 基础公司表 (`listed_company_base`)

作为整个数据库的锚点根表，后续所有的业务表（公告、套保明细、主营业务）都通过 `stock_code` 与之关联。

- `stock_code` (CHAR(6), 主键): 股票代码（如 000001）。
- `company_name` (VARCHAR(100)): 公司全称。
- `company_short_name` (VARCHAR(50)): 公司简称。
- `market` (VARCHAR(20)): 所属市场（如 SZSE 深交所、SSE 上交所等），建有索引方便过滤。

**数据来源**：通常不需要大模型去猜，可以由爬虫在抓取公告前（或同步）从巨潮资讯网等公开渠道批量导入的基础数据字典。

### 2.2 年度主营业务表 (`company_yearly_main_business`)

记录每一家公司在特定年份的主营及行业归属。

- `id` (INT, 主键): 自增主键。
- `stock_code` (FK): 外键，关联基础公司表。
- `biz_year` (SMALLINT, 索引): 业务年份（例如 2024）。
- `main_business` (TEXT): 详细的主营业务描述段落（可由财报爬取或大模型总结）。
- `industry_class` (VARCHAR(50), 索引): 标准行业分类（如“有色金属冶炼”、“汽车制造”）。
- `business_core` (VARCHAR(200), 索引): 核心业务关键词（如“铜加工”、“生猪养殖”），**这是用来做同业聚类比对（需求4）的最关键字段**。

**约束**：`UNIQUE(stock_code, biz_year)`，确保一家公司在一个年份只有一条主营业务记录。

## 3. 使用场景与读写逻辑说明

### 场景 A：写入大模型的主营业务分析结果

如果你未来开发了“主营业务分析”的 LLM 模块，该模块分析完某公司的年报后，输出该公司的 `industry_class` 和 `business_core`。
**操作**：通过类似 `update_or_create` 的逻辑，以 `(stock_code, biz_year)` 为联合检索条件。如果有则更新 `business_core` 和 `industry_class`，如果没有则新建。这保证了数据的幂等性。

### 场景 B：查询某行业的套保渗透率（由咱们目前后端的 `/api/compare/hedging_by_business` 接口实现）

1.  **确定基数**：前端传入 `year=2024`，`business_core=铜加工`。后端首先去 `company_yearly_main_business` 查出所有符合这两项条件的公司列表（假设有 10 家）。
2.  **查找套保**：拿这 10 家公司的 `stock_code` 去 `hedging_business_detail`（由公告大模型生成的表）里查，看这 10 家在 2024 年有多少家有套保记录（假设有 4 家）。
3.  **计算并返回**：计算出渗透率为 40%，并合并展示这 4 家公司的套保额度总和及涉及的商品种类。

## 4. 总结与改进建议

目前关于大模型直接输出到数据库的设计是非常合理的，整体架构如下：
**[外部触发/定时任务] -> [大模型模块处理] -> [输出标准化 JSON] -> [通过 HTTP POST 发给 FastAPI Webhook 接口] -> [FastAPI 负责解析 JSON 拆解落地到不同业务表]**

这样的好处是：

1.  **解耦**：大模型执行很慢，如果直接和 FastAPI 强绑定容易导致超时卡死。
2.  **易维护**：FastAPI 只负责校验 JSON 格式对不对，负责把复杂的数据关联（比如找不到商品就自动新建商品、找对旧记录更新额度）做在接口里。大模型那边只需要“傻瓜式”地吐出结果即可。

对于现有的 `hedging_business_detail` 数据库，没有修改必要，目前的 Schema（已经帮你建好了对应的 Tortoise ORM模型）完美迎合了这种“大模型到数据库”的映射模式。你需要做的就是在大模型跑完后，发一个 POST 请求给目前后端挂载的 `/api/announcements/{id}/parsed` 即可。
